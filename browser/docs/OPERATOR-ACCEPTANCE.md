# PEA Web operator acceptance checklist

Use this after installing or updating a specific PEA Web build. These are **operator tests**, not a claim that a particular deployment or cloud provider has passed. Record the date, app version/commit from the footer, hosting topology, browser/device versions and pass/fail/blocked for each applicable item. Use a dedicated test account, test folder and synthetic content. Never put credentials, tokens, personal transcripts, screenshots of private data, or customer data in issue reports or shared test results. Tests that create external files or use model APIs need your explicit choice; check provider charges first.

PEA Web is work in progress: there is no finished installer or production signed release. The current gateway is for an owner/trusted household, with a single bearer token, not an Internet-facing multi-tenant service. The local package is the primary supported delivery target; an operator-managed Docker deployment on GCP or AWS is a documentation-only path, with no supplied image or validated cloud recipe yet. A cloud instance needs the controls below. Internet access for unrelated users requires operator-designed authentication, isolation, abuse controls and a production security review; the single gateway token does not provide these.

## 1. Record the source and run offline checks

- [ ] Record the source revision, installed program version, service process and actual URL separately. Confirm the footer version/commit match the version you intended to install; source checks do not prove the installed runtime was updated.
- [ ] In a **source checkout** with Node 20+ and Python 3.11+, run `python3 tools/check_repository.py`, `python3 browser/server/check_source.py`, `node --test browser/tests/*.test.mjs`, and `python3 -m unittest discover -s browser/server -p 'test_*.py' -q`. The index scan applies to a checkout with Git, not necessarily an installed package. Record the exact revision and results. Synthetic loopback sockets must be available.
- [ ] In Updates, use the explicit main-branch comparison and published-release check; verify the displayed installed commit and understand that a differing main commit does not itself install an update or establish ancestry. Check that modified/unknown identity is disclosed.
- [ ] For packages, independently verify the release signature with a separately trusted signing key; follow [updates and rollback](RELEASES.md). A matching footer alone is not signature verification. Confirm the previous verified version and a restore plan before updating.

## 2. Host and network boundary

- [ ] On a build with the local helper, run `python3 browser/server/local.py setup` once, then `check` and `start`; verify setup refuses to overwrite the token and stopping the foreground process stops the gateway. Skip setup if a token already exists. Confirm no service, browser launch or model download was performed.
- [ ] Confirm the gateway binds to loopback, the model server listens only on loopback, and the gateway's upstream is the intended local model server. Its token is stored outside the repository, owned by the service account and readable only by that account. Do not paste its value into commands, logs, chat, or screenshots.
- [ ] For a private remote setup, use an authenticated network/VPN and a trusted HTTPS reverse proxy; configure the exact `--public-origin` used by that proxy. Verify the proxy forwards Host/Origin and streaming without buffering, and use the same HTTPS origin for the UI and gateway. A VPN without HTTPS does not make a browser origin secure.
- [ ] From an authorized device, verify the HTTPS certificate, page load, Chat/Today/Greenhouse navigation, and no failed application module requests in browser developer tools. From an unauthorized network, verify the instance and upstream are unreachable. If the design includes Internet access, verify the separately designed edge authentication, authorized-user boundaries and abuse protections before adding accounts or data; the gateway token by itself is not a multi-user access system.
- [ ] On GCP or AWS, verify your own VPC/subnet firewall or security-group rules, identity/IAM, private ingress and egress, service-account permissions, secret storage and logging. Avoid public model ports and unauthenticated storage; check the actual deployment configuration rather than assuming a cloud default. Verify the proxy can reach the loopback-only gateway and that any local model upstream shares its network namespace; being on the same host in separate ordinary bridge containers is not sufficient. Cloud Run ingress and other managed platforms may require a separate proxy or architecture, as described in [self-hosting](SELF-HOSTING.md). Budget for VM, disk, network and model hardware costs; a cloud-hosted local model is not free infrastructure.
- [ ] Restart the private service and proxy intentionally and verify recovery, origin enforcement and certificate renewal. Check that reverse-proxy, host and model-server logs do not retain authorization headers, request bodies or private transcripts. Review backups and deletion policies you control.

## 3. Model route and privacy

- [ ] Using a dedicated test key or a local model, connect only the route you intend. Verify Chat and Greenhouse show their selected models, privacy/cost disclosure appears before sending, changing the model/profile prompts for a new review, and a failed route does not silently switch to a paid provider. Check the provider's current price and retention terms yourself.
- [ ] For a local model, select it in the browser, send a synthetic prompt and verify a streamed answer. With the token absent or invalid, model routes must reject access. An unsupported or remote model upstream must not become an open proxy. Never send the bearer token in a URL.
- [ ] If using the iPhone app against this gateway, use your own HTTPS origin and token; verify model listing and a synthetic chat from the physical phone over the intended VPN. Record iOS and app versions. The iOS client and browser do not automatically share keys, settings, history or permissions.

## 4. Conversation, memory and recovery

- [ ] Create synthetic Personal and Work conversations and verify neither appears in the other profile or Blended. Review an owner-sourced memory, check its source and sharing switch, and verify no memory is sent without the separate provider review.
- [ ] Enable encrypted library saving with a unique test passphrase. Lock, reload, unlock and explicitly continue a conversation. Verify a wrong passphrase does not overwrite the saved library and that a competing-tab conflict is reported rather than silently overwritten.
- [ ] On a build containing the backup feature, download a backup and restore it into a **separate empty browser/origin**. Unlock and verify both profiles and memories. Verify a wrong passphrase or altered file is rejected and a browser with existing saved data is not overwritten. Check your downloaded file and passphrase are retained safely. Backups do not include the task board, files, credentials or grants; restore is not automatic sync or an iOS archive import.

## 5. Optional connected services and actions

- [ ] Google: with a dedicated test account, configure your own Web OAuth client and the exact HTTPS origin. Review the broader Drive scope, create/select a test PEA folder, move in a test file manually and verify it is visible. Verify another file outside the selected folder is not offered by PEA. Provider permission is broader than PEA's app-enforced folder boundary.
- [ ] With a test folder, review and create a harmless document and simple unpublished form, then verify title, contents, location and that no sharing changed. Test rename and recoverable Trash only on disposable test files. If the response is interrupted, check for a partial file before retrying.
- [ ] Calendar/Gmail peeks: if enabled, verify read-only previews and profile isolation; disable their separate model-sharing switches and confirm a model review excludes them. Direct calendar writes are not implemented. For a build containing event drafts, review a synthetic event including local and UTC time, download its file and manually import into a disposable calendar; check the time and confirm no invitations were sent.
- [ ] In Chat and Greenhouse, use synthetic prompts to test story, email, document and form proposals. Cancel each review and verify no external change. For approved story capture, verify the reviewed title, scope and completion criteria appear on exactly one Inbox story with no automatic execution; cancel must leave the board unchanged. In two tabs with the same synthetic encrypted board, save different changes and verify the stale tab reports a conflict, retains its unsaved view, and warns before reloading the saved board. For email, verify the reviewed recipient/body and open a test draft without sending. For documents/forms, editing the draft alone must not create a file; creation requires the separate folder review. Proposals are not restored as actions after reload.
- [ ] GitHub/image tools are optional and may incur charges or trigger repository CI. Use a dedicated test repository and limited token; inspect the destination and draft PR before approving. For image models, review the quoted price and ceiling before generation. No generated code should execute automatically.

## 6. Device experience, operations and rollback

- [ ] Check desktop and narrow mobile layouts, both themes, transparent icon, keyboard focus, scrolling, keyboard navigation, screen reader labels and visible errors. Walk through the OpenRouter, local model and Google setup choices without connecting; verify Back and View all settings. Walk forward and back through the interview, skip optional fields, save synthetic answers, and verify profile and sharing boundaries. On Android/iPhone, test the private HTTPS URL and VPN reconnect. Record physical devices; simulator and source checks do not establish device acceptance.
- [ ] With explicit microphone consent and synthetic speech, test dictation, stop, profile changes and reading a reply. The browser/OS may process speech online. Do not assume locked-screen or AirPods background reliability in a web browser; test the native iOS client separately if those are required.
- [ ] Verify resource use, disk space, network access, model cold starts and restart behavior on the target host. Observe provider/cloud spending with your own controls; model unit-price display is not a monthly hard cap.
- [ ] Before changing versions, save and test encrypted backups on a separate empty origin. Exercise the verified update and rollback process in a disposable installation; confirm the expected version, model endpoint, vault unlock and config after restart. A program rollback does not roll back browser IndexedDB or external Google/GitHub changes.

Record failures with the build identity, test section, expected and observed behavior, browser/device, and sanitized logs. Treat any untested item as **not yet verified** rather than passed. See [self-hosting](SELF-HOSTING.md), [memory and recovery](MEMORY.md) and [parity](PARITY.md).
